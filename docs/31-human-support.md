# 人工咨询闭环

2026-09-15。本阶段交付业务功能，未扩充模型评测，也未调用付费模型。

## 如何体验

1. 客户登录 `/app/assistant`，点击工具栏「转人工客服」。系统带入最近三轮的问题与助手最终回答摘录；客户可修改主题、补充问题、删去不想交给客服的内容，再点击「确认提交咨询」。无需配置模型也可发起咨询。
2. 提交后进入 `/app/support`。该页也在客户侧导航中，可新建独立咨询、补充消息和查看处理状态。
3. 另开浏览器会话，以现有客服账号登录 `/service/support`，从「人工咨询」入口查看工单。点击「领取咨询」后回复客户；其他客服只能查看，不能代替领取人回复或解决。
4. 客户与客服可以继续交换文字消息。页面可见时每五秒轮询更新，支持手动刷新；没有浏览器推送或离线消息通知。
5. 领取客服至少回复一次后，可「标记已解决」。结束后不能追加新消息，有新问题可新建咨询。

这是独立的文字咨询工单，和现有订单售后申请并列。咨询本身不创建售后单、不审批退款、不改订单或库存；客服仍需到对应业务工作台核实和操作。当前不含自动转派、重开、附件、在线状态、未读角标或 SLA。

## 设计与实现

- 独立页面：客户 `/app/support`、客服 `/service/support`。管理员使用现有员工权限也可查看/领取咨询，只有领取人可以处理。每次请求重新校验在职员工与角色记录。
- 状态：`WAITING`（等待客服）→ `IN_PROGRESS`（处理中）→ `RESOLVED`（已解决）。领取/回复/解决均为 MySQL 事务。
- `aster_support_ticket` 保存客户归属、主题、客户确认的背景摘录、状态、领取人及时间。
- `aster_support_message` 保存有序文字消息和领取/解决动态，使用自增序号排序，避免同一秒多条消息随机排顺序。
- `SELECT ... FOR UPDATE` 将领取、回复、解决串行化到同一工单行。两位客服同时领取时只有一位获准；同一领取人重试不会重复生成领取动态。
- 创建工单和发送消息使用 UUID 请求编号。相同内容重试不重复写入；编号相同而内容或归属不同被拒绝。结束操作也可重复请求。前端失败重试保留当前内容的请求编号；刷新整个页面或重新开始新的提交不属于同一请求。
- 客户身份取自登录账户，接口不接受请求者自报的会员 ID。读取和回复都检查工单归属；客服回复与解决再次检查领取人。
- 列表每页二十条，按创建时间和 ID 排序；消息在一条咨询达到 190 条时限制继续写入，详情上限二百条，留出系统动态空间。当前列表采用 offset 分页，不宣称并发插入时绝无跨页重复。
- 摘录最多 6,000 字，主题最多 120 字，单条消息最多 2,000 字。摘录由前端从当前会话整理，经客户确认后保存；它是**客户提供的背景**，不是服务器证明的聊天历史，也不是自动生成且已验证的业务摘要。不会自动带入 API 配置、原始工具内容或确认令牌；客户仍可在提交前编辑文本。
- 摘录与消息按普通文本显示，不执行其中的 Markdown/HTML 或指令，不交给模型作为审批依据。

核心代码是独立编写的 `SupportService`、两侧 `AsterSupportController`、前端 `Support.tsx`。沿用现有 Spring Boot、JDBC、React、登录与角色校验，不新增框架依赖。既有 Agent 服务、MCP、商品和政策功能保持各自职责；从聊天点击转人工会创建独立咨询，并不会自动停止已经启动的 Agent 后台执行。

## 部署

新增可重复执行迁移 `deploy/mysql/migrations/008-support.sql`，只建两张人工咨询表及相关索引/外键。`scripts/init-p1.ps1` 已接入该迁移，`start-p2.ps1` 调用初始化流程时会执行。现有本地数据库已经应用，新 Java 包和前端产物已部署。

从源代码启动可继续使用：

```powershell
./scripts/start-p2.ps1 -Build
```

无需新增环境变量或模型密钥。咨询消息与订单相同存于现有 MySQL 数据卷，重启保留。
