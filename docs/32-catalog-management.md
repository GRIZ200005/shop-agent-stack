# 商品管理与库存调整

2026-09-16。本阶段推进可操作的业务页面，不扩充模型评测，不调用付费模型。

## 使用方法

1. 使用管理员账户登录 `/admin/products`，或点击左侧「商品管理」。客服账户无此管理权限，后端每次请求核验角色。
2. 按商品名称搜索、按在售/下架筛选，每页20件。列表展示图片、分类、价格和状态。
3. 点击「管理」，选择规格，查看总库存、订单占用量和可售库存。
4. 填写调整数量（正数补货、负数减少）及原因，点击「保存库存调整」。上下架也必须填写原因。
5. 查看最近30条调整记录，包括管理员、时间、SKU、变化前后数值和原因。操作编号只用于内部幂等，不作为商品名称展示。

客户重新查询商品后会读取最新状态。Agent 已有商品工具也从同一 MySQL 商品/SKU 表读取并校验快照；本轮没有用真实模型复测回答，也没有实现浏览器主动推送更新。

当前管理现有商品，不包含新建商品、图片上传、编辑商品描述/价格、多仓库、采购单或批量导入页面。商品仍是原创合成商品，不宣称真实商家库存。

## 后端设计

- 原创 `CatalogManagementService` 与管理员 `/aster/catalog` API；没有增加新依赖。
- `aster_catalog_change` 在同一事务内记录成功的库存/状态变化；请求编号唯一，相同请求重试不重复调整，编号复用但内容不同则拒绝。
- 库存调整按「当前总库存 + 调整量」计算，提交的旧库存值必须和数据库一致。锁定商品行后锁定SKU行；调整后不能低于订单占用量，不能负数或溢出。不会重置 `lock_stock`、销量或历史订单。
- 上下架检查旧状态；下架后既有客户商品详情和 Agent 商品查询均不再返回该商品。
- mall 的下单占用库存代码改为原子条件更新：重新检查商品可售状态，再要求 `stock - lock_stock >= quantity`。按商品/SKU排序占用，处于原有下单事务中，后续失败整体回滚。它修复了本路径的先读后覆盖窗口，不代表整个系统所有订单/取消/支付链路均已完成并发审计。
- 前端网络结果不确定时保留原请求编号供重试。服务器明确拒绝后可修改并重提；关闭弹窗、刷新页面后不保证保留原请求，重新操作前应刷新并核对历史记录。
- 审计表覆盖新增管理接口，**不覆盖上游遗留管理API、直接SQL和所有订单库存流转**，不是完整仓储流水账。SPU的旧 `stock` 字段不作为可售库存权威来源。

## 部署与验证

新增 `deploy/mysql/migrations/009-catalog-management.sql`，已接入 `scripts/init-p1.ps1`。现有数据不重置。构建使用 `scripts/build-p0.ps1` 和 `apps/web` 下的 `npm run build`，按现有 Compose 流程启动服务。

必要验证：

- Java 聚焦回归31项通过，其中新增4项覆盖库存幂等、旧值冲突、占用量下界、下架禁止占用、事务回滚及两线程竞争库存。
- Playwright `tests/catalog-management.spec.ts`：管理员页面及真实MySQL调整、客服越权拒绝、重复请求/旧值冲突、下架屏蔽客户详情；另验证实际创建未支付订单。
- 下单补充测试首次误调用明确禁用的旧取消接口，返回403。保留禁用边界，测试改为在 `finally` 中通过Docker/MySQL清理**本次合成用户的指定未支付订单**：释放占用并保留关闭的订单记录。这是测试夹具清理，不是已交付的客户取消功能。测试要求本机Docker可用。
- 商品管理验收补货后使用相反增量撤回，不用旧绝对库存覆盖当前库存；恢复测试商品上架状态。管理员审计记录保留，原因明确标记验收。

本阶段没有新增模型准确率、吞吐量或生产并发能力结论。后续建议补管理员订单履约页面（筛选订单、模拟发货、客户查看物流），再考虑更大范围的后台经营管理。
