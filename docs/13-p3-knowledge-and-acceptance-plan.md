# P2 验收与 P3 知识工程实施

日期：2026-09-15。阶段目标是可审计、可引用、可评测的业务助手。数据量分别统计文档、条款、SKU、订单与场景族，不能把切块或同义改写数量当成独立业务规模。

后续进展：正式政策的 P3a 基础检索引用闭环已完成本地验证，最新范围与记录见 [14](14-p3a-policy-rag.md)。下文的离线基线仍保留作为该轮历史记录，48 篇草案未自动发布。

## 本轮落地

1. `evaluation/p2-acceptance.tsv`：24 个 P2 验收场景，注明前置条件、预期结果、禁止副作用和判定方式。它是验收清单，不是已经全部跑过的真实模型成绩。
2. `knowledge/authoring/policies.tsv`：48 篇独立商城草案、144 条条款，9 类业务主题。全部 DRAFT，未覆盖线上政策。
3. `knowledge.py`：LangChain Core Document 标准文档、条款级 BM25 基线、可见性和生效时间过滤、版本冲突阻断。
4. 独立 24 题开发集、哈希 manifest 与离线评分脚本。只报告实际检索结果，不将固定规则测试算作模型效果。

P2 的 UI、MCP、确认事务与模拟业务已有回归；用户已成功体验模型查询订单。完整真实模型验收仍需专用合成账户的模型配置或用户在已登录页面操作。现有个人加密配置不会被复制给新测试账户，也不会从浏览器或数据库提取原始密钥。运行清单不默认触发 24 次付费调用。

首批真实 smoke 先选 P2-01、02、07、09、10、16 六项，最多八次用户请求；超时和失败全部记入分母。P2-11 明确使用模拟交易，随后核对唯一申请与审计记录。攻击、重试和故障注入优先用隔离的确定性自动化，避免把系统性质归因于模型。

记录 run_id、场景 ID、实际模型标识、数据版本、首段正文时间、总耗时、报告 token、业务结果与失败类别。缺少价格快照时只报 token，不估算成确定金额；当前事件尚不包含全部计时字段，批量评分器需要补齐。

## 来源核查与迁移决定

旧学习项目的准备报告记载 1386 片段，其中银行知识 1372、零售政策 14；该报告对应的本地 data 原文目录当前不存在。这是旧报告数字，不能视为新库真实库存。其 README 指向公开 tau 数据来源，但没有足够的本地原文版本证据支持直接迁移。

迁移规则：零售公开材料固定公开源提交和许可证后再评估；银行资料与当前商城主题不符，不加入正式检索库；旧问答标签与运行日志不进入知识库。可学习标题切分、BM25/向量融合和重排这些通用方法，独立实现。不能复制私有提示词、内部地址、代码或专有资料。

[公开 tau 仓库](https://github.com/sierra-research/tau2-bench) 当前文档已有版本和评分变更说明，因此不使用浮动 main 下载后沿用旧成绩。新业务语义与原任务不完全一致，成绩仅称为 Aster 自建评测。

## P3 分步交付

### P3a：发布与索引闭环

先扩展 Java/MySQL 政策版本、生效时间、可见性、撤回与分页读取；现有政策列表只返回最多 100 条，不能直接用它构建完整大库。发布触发索引任务，失败可重试；请求回答前核实引用版本仍可见。草稿不得对客户泄露。管理员能看到发布与索引状态，客户能打开引用原文。

第一条闭环：管理员发布一篇审核政策 → 检索找到准确条款 → 模型引用回答 → 撤回后无法继续引用。随后批量扩展资料。

### P3b：Hybrid 检索

保留 BM25 基线，加入支持中文的嵌入检索、融合与重排。向量服务与模型按当前机器资源实测选择并固定版本，不能沿用旧英文嵌入配置直接假定中文效果良好。嵌入配置与聊天模型分开，因为兼容聊天 API 不代表支持 embeddings。

LangChain 组件用于文档、切分、嵌入/检索接口；保留自研的权限、生效时间和引用校验。输出可追踪到 clause_id/version/hash，知识检索不用于获取私有订单数据。

### P3c：LangGraph 有界 Agentic RAG

查询本人订单（必要时）→ 检索 → 检查证据是否足以回答 → 回答并引用 / 改写后补查 / 补问 / 明确无法判断。检索最多三轮，另设总耗时和 token 预算。引用证据只作为数据，不能改变工具权限；资格说明不能替代 Java 业务校验或用户确认。

把“拆封耳机能退吗”做成需要订单事实、商品使用情况和政策依据的多步骤任务。证据不足不能强行认定符合或不符合，草案中的能力说明也不能当成完整商业退货政策。

### P3d：受控网络补充

联网仅补充公开知识，保留来源；缺本店政策不能借用其他平台条款。先快照回归，再真实网络 smoke。外部电商 MCP 排在 v1.1，不与知识库一起无边界扩张。

## 框架分工

已经运行 LangGraph 1.2.11；现有依赖包含 langchain-core 1.6.3，本轮开始直接使用 Document。LangGraph 负责状态、分支、工具循环和预算；LangChain 组件用于检索生态，不再套一个重复 Agent 主循环。[官方说明](https://docs.langchain.com/oss/python/langgraph/overview)明确两者可以组合，LangGraph 也可独立使用。

Java/Spring Boot 保持业务事实与权限的所有者；MySQL 管理正式政策、业务数据与索引任务；Redis 后续承载带版本键的缓存，不能作为唯一政策依据；Python 管理检索与 Agent；TypeScript/React 显示过程、引用和确认。现有 Redis 已部署不等于本轮已实现检索缓存。

## 评测门槛

- 当前小开发集先揭示问题，不作为最终质量门槛；正式评测按 03 文档。
- 分别报告条款 Recall@5、引用支持率、无答案拒答、版本/权限正确性与端到端成功率。
- 固定模型与问题，对比无 RAG、单次 Hybrid、Agentic RAG；报告补查新增正确数和额外成本。
- 版本过滤与非法写操作用确定性反例验证，语义支持人工抽查；不能只用字符串包含或 LLM 自评判成功。
- 每条证据指向具体代码、测试和原始结果；未实现或未验收项明确保留。
