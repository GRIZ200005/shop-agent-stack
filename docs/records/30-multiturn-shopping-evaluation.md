# 多轮选购与混合问题评测

> 验证记录：结果与限制对应文中列明的运行日期及配置。当前使用方式见[工程文档](../README.md)，不同实验结果不合并为统一准确率。

日期：2026-09-15。本阶段沿用已保存的个人 DeepSeek 连接，不要求重新填写 API Key。

## 当前新增能力

会话任务支持预算 `budget`、品类 `category`、需求 `requirements` 三类原文偏好，仍只接受当前用户原文，不能由模型伪造价格、授权或业务状态。用户更正时覆盖对应字段；明确换话题时要求重置。原有会话无需迁移数据库。

每次商品回答经过商品与政策复核后，宿主把最多五件商品的 ID、名称保存到 `recent_products`，与成功结束状态原子提交。这里不保存价格、库存、规格或完整工具内容。新问题中的“这款”可依此定位后重新查询；多个候选无法判断指代时要求补问。模型不能通过任务记忆工具直接写这些商品 ID，失败或停止执行不会提升新的引用记录。

混合问题的政策检查器只检查服务政策部分，商品容量、材质和价格仍由商品工具核实。回答发布前，两类引用都要通过既有的当前来源校验；政策撤回时，即使商品仍有效也不发布这份混合答案。

商品引用校验失败时，新增一次受四轮模型和 Token 阈值共同约束的草稿修正机会。允许重新查询或删去没有依据的历史商品陈述；修正后仍不合格则失败。它不是静默接受旧引用，也不代表已经实现逐句语义蕴含校验。已有商品记忆的续问会先缓冲模型文字，避免未经复核的旧商品草稿提前流出。

## 题集和计分

`evaluation/shopping-dialogues-v1.json` 共 **12 组、24 轮**，开发集与预留集各 6 组、12 轮。包含预算更正、单一/歧义指代、换话题、用户错误价格声称、尺寸比较，以及商品和政策混合提问。

题集哈希及分组冻结规则在 `evaluation/shopping-split-manifest.json`。每轮都有期望商品、必要政策标题或工具条件，并附人工答案判定要点。答案要点只供评测，不进入模型请求。

预留集尚未调用模型，也不用于调提示词。**这仍是同一项目作者编写的合成预留集，不是外部独立盲测基准。** 部分任务能力与既有商品开发题相近。若查看其模型表现并据此修改系统，应将相应用例转入下一版开发集，重新准备未用于调参的预留题；正式准确率仍需要独立复核标注。

自动检查及分母分别记录：

- 执行完成率：COMPLETED 轮数 / 计划轮数。完成并不等于正确回答。
- 商品证据覆盖：包含指定商品引用的轮数 / 有该标注的轮数。
- 预算检查：推荐引用标价范围，或预算更正后的查询过滤参数。用于解释价差的超预算引用与“符合预算的推荐”需要人工区分，因此负例不机械禁止所有超预算引用。
- 政策证据覆盖：包含指定政策标题引用的轮数 / 有政策标注的轮数。
- 话题切换检查：不继续引用被排除的商品、不无故继续查政策。
- 工具边界：评测只允许商品和政策读取；试图调用订单或售后操作会被记录并阻止。真实运行工具结果未被替换，测试客户不会创建订单或退款。
- 全部契约通过：一轮所有适用自动条件同时成立。**它不是答案准确率。** 空商品标签不算“商品检索成功”，也不会人为增加商品证据检查分母。

每次评测保存独立事件库、逐轮工具和回答、源码/题集/目录哈希、请求数、服务商报告 tokens、耗时，以及 `review-template.json`。人工复核尚未填写时，`answer_accuracy` 保持 null，不把未审核答案算作正确。失败、不执行及缺少记录的数量可从 planned/recorded/status 区分；不因后续轮次成功而抹去前轮失败。

## 本阶段实际证据

使用 `deepseek-flash`，真实 LangGraph → MCP → Java → MySQL。评测直接调用线上同一 runtime 入口，使用隔离会话数据库；没有经由 Agent HTTP/SSE 发起这些付费请求。页面沿用现有 SSE 和商品卡片渲染，本阶段未修改前端。

| 实验 | 计划轮数 | 自动契约通过 | 模型请求 | 报告 tokens |
|---|---:|---:|---:|---:|
| 首轮：预算、指代、混合问题三组 | 6 | 5/6（83.3%） | 15 | 43,751 |
| 预算组定向复测 | 2 | 2/2 | 6 | 17,909 |

首轮目录：`shopping-dev-20260915T141003Z-1062b6`。预算第二轮把过滤条件从 50 元改成了 20 元，但模型在零结果后继续用了未经本轮查询的旧商品引用，被系统正确拦截，因而该轮仍计失败。其余轮次正确重查了保温杯，并在混合问题中引用茶壶容量和“预览不退款”政策；下一轮要求只谈商品时没有继续调用政策工具。

复测目录：`shopping-dev-20260915T141244Z-d3cc8e`。预算更正后回答“本轮没有符合条件的商品”，两轮自动检查均通过。本次模型未触发新增的草稿修正分支，因此不能把这次成功全部归因于修正机制；**修正分支由确定性测试验证**。模型仍提到上款商品超预算，虽与当前目录相符，但没有对上款再次单独读详情，说明按引用 ID 校验并不能捕获全部无引用的事实推断。

合计 21 次付费请求、61,660 reported tokens。两次实验不合并成整体成功率；最终版本尚未重跑开发集全部 12 轮。预留集 12 轮未运行；没有发布独立答案准确率。

回归证据：97 项 Python/评测测试通过、7 项需本地服务的测试按默认规则跳过；随后新增的冻结题集校验单独通过，共 98 项。覆盖偏好更正、历史截断后商品引用保留、禁止模型写宿主引用、失败不提升记忆、旧引用草稿修正、混合来源撤回时禁止发布、计分分母与未完成记录。Java 和前端本阶段无功能改动，未重复其完整回归。

## 运行方式与下一阶段

默认只校验题集，不调用模型：

```text
python scripts/evaluate-shopping-dialogues.py
python scripts/evaluate-shopping-dialogues.py --split reserved
```

明确授权的真实开发测试使用 `--live --saved-member <配置账户编号> --cases dev-budget,dev-reference,dev-mixed --max-requests 28`，在已有 Agent 依赖环境内运行，并按上一阶段配置本地 Docker 网络、仓库挂载和模型连接数据卷。密钥只在内存解密，不写入题集、评测 JSON 或测试客户账户。

现在可在星序助手同一会话中连续问“查远山保温杯规格”→“刚才那款能放微波炉吗？”，或者“茶间壶容量多少，售后预览会直接退款吗？”→“只讲这把壶能否明火加热”。新会话与其他用户不会共享任务记忆。

下一步先进行逐轮答案人工审核，补充歧义指代、重置偏好与长对话截断场景的真实测试，再运行未用于调参的预留集。需要特别关注：缺少引用的事实陈述、否定条件、无结果后的旧商品复述，以及混合问题中一个部分无证据时如何给出明确的部分回答。通过这些门槛后再比较商品语义检索与关键词检索，不能用检索命中率替代完整任务质量。
