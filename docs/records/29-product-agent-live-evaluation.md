# 商品 Agent 接入与真实模型开发验证

> 验证记录：结果与限制对应文中列明的运行日期及配置。当前使用方式见[工程文档](../README.md)，不同实验结果不合并为统一准确率。

日期：2026-09-15。商品目录提交为 `e4198a1`。本阶段在该目录上增加原生业务工具，不把商品价格、库存写进政策向量库。

## 已实现的链路

客户提问 → 已保存的个人模型连接 → LangGraph 决定工具 → MCP SDK → Java 短期执行授权 → MySQL 商品/SKU → 引用复核 → 中文回答与商品卡片。

- `search_products`：最多四个短关键词 AND 查询名称、规格、用途等字段，支持精确分类、含边界的标价范围；每页五件，ID 游标续查。SQL 使用绑定参数，`%`、`_` 按字面处理。
- `get_product`：只读取未删除且已上架商品；包含商品规格、注意事项和 SKU 可售库存 `max(stock-lock_stock,0)`。两条内部 Java 路由均验证执行授权。
- 商品证据使用 `[G10001]` 等引用。答案引用的商品会再次读取并比较规范化 JSON 的 SHA-256 快照；资料变化、下架、未知引用或遗漏引用会中止输出。检索后的文字在复核前不向页面流出。
- 页面仅从复核成功的 `product_sources` 事件生成商品卡片，点击进入 `/app?product=10001` 并打开详情。原始搜索候选不会直接变成推荐卡片。
- 商品工具只读；加入购物袋、下单和库存修改仍由现有业务界面完成。标价不是结算报价，查询库存不构成库存预留。

商品检索目前是 **MySQL 关键词与结构化筛选**，不是商品语义 RAG。政策继续使用既有 Hybrid/RRF/Rerank 与证据检查机制。工具说明明确区分商品兼容性和服务政策，仍需更多混合意图测试来验证模型选路稳定性。

### 真实模型首轮

使用用户已经保存的 **DeepSeek / deepseek-flash**，不重新输入密钥。密钥仅在内存解密，通过只读 SQLite 连接读取；不复制到测试客户，不记录到报告。SQLite WAL 协调文件需要可写目录，评测的会话数据库另建于被忽略的结果目录。

从 `catalog/search-cases.json` 的 20 个自建开发场景中选取索引 `0,1,4,9,10,11,14,19`，共 8 个单轮用户问题。每例运行真实模型和真实 MCP/Java/MySQL，使用独立合成客户；没有模拟模型响应，也没有替换业务工具结果。测试调用与线上相同的 `runtime.execute` 入口，**没有经由 Agent HTTP/SSE 路由发起这些付费请求**；浏览器事件渲染另测。

首轮记录 `product-live-20260915T135235Z-858b64`：

- 执行完成：7/8，87.5%。其中一次虽然标记完成，实际只返回证据不足，不能算任务成功。
- 自动契约全部通过：6/8，75%。条件为执行完成、引用覆盖预标注商品、未调用不允许的业务工具。
- 19 次模型请求，服务商报告 49,027 tokens；单场景耗时中位数约 4.51 秒，最慢 9.18 秒。
- 按预期要点逐项阅读：容量、预算玻璃杯、木砧板养护、有线键盘、卷口袋潜水限制均得到有商品依据的回答；认证场景没有虚构报告，但没有执行商品查询。该场景预期商品集合为空，其证据检查自动通过，不代表测出了检索能力。
- 扩展坞兼容性误走政策检索，未提供有效答案；内胆包尺寸在第三轮后失败。两例均保留在首轮分母内。

这组数据是开发烟测，**75% 是自动契约通过率，不是独立回答准确率、Recall@K 或线上成功率**。读取过所引用的商品也不能证明答案每个事实都蕴含于证据；自动语义判定和独立人工双人标注仍未完成。

### 故障诊断与定向复测

| 独立记录 | 场景 | 自动契约 | 请求数 | 报告 tokens |
|---|---|---:|---:|---:|
| `product-live-20260915T135426Z-c72d7e` | 尺寸诊断，无业务修复 | 1/1 | 4 | 11,750 |
| `product-live-20260915T135559Z-4c3961` | 工具说明调整后的兼容性与尺寸 | 1/2 | 6 | 17,929 |
| `product-live-20260915T135837Z-e9c899` | 预算修复后的尺寸 | 1/1 | 2 | 5,223 |

诊断发现：尺寸场景可能在查商品后额外更新任务记忆，第三轮累计用量超过原 8,000 阈值，下一轮被拒绝。MCP 的 AnyIO 异常组包装使受控错误显示成了通用服务错误。

修复内容：

1. 细化商品/政策工具分工，避免纯兼容性问题无谓检索政策。兼容性复测给出了“主机 USB-C 接口需支持视频输出”，并引用商品 10053。
2. 新工具目录增加了每轮输入开销，将继续请求的软阈值调整到 **16,000 reported tokens**；保留四轮外层模型、八次工具和 90 秒时限。最后一轮不再提供工具定义，要求根据现有证据回答或补问。
3. 解开单原因异常组，保留受控预算提示；服务日志只记录错误类型与代码位置，不打印异常原文、模型内部推理、请求局部变量或凭据。多原因异常仍显示通用错误。
4. 确定性测试覆盖“三轮累计 9,000 后第四轮收尾”和包装错误提示。最后一次真实尺寸复测只用了两轮，因此它证明该次端到端成功，**预算阈值分支的证据来自确定性回归**。

四次运行合计 31 次付费请求，报告 83,929 tokens。不同配置、不同样本的结果不混合成新的整体准确率；也不能将失败用例定向复测称为“全量 100% 通过”。首轮全部八例尚未在最终版本上重跑。

## 如何使用和复现

刷新客户页面，进入「星序助手」，继续选择已有个人模型。可提问：

- “推荐 50 元以内的玻璃杯。”
- “榉木切菜板可以放洗碗机吗？”
- “任何 USB-C 电脑插扩展坞都能连接显示器吗？”
- “我的电脑机身 34×24cm，可以装进护行内胆包吗？”

真实评测脚本 `scripts/evaluate-product-agent.py` 必须显式 `--live --saved-member <已授权配置账户编号>`；不属于默认回归流程。`--indices 10,11` 可定向运行，不指定时为首轮八例；每次脚本最多 32 次模型请求。Docker 运行时加入本地网络、复用 Agent 数据卷与密钥挂载、把仓库挂到 `/workspace`，设置 `ASTER_PORTAL_URL` 与 `ASTER_MCP_URL`。

每次新建 `evaluation/runs/product-live-*`，保存脚本/Agent 源码/目录/题集哈希、独立事件数据库、逐例 JSONL、用量和摘要。不会覆盖之前的结果。原始材料保持 Git 忽略，只发布本文件等经过审阅的摘要。

限制：16,000 是下一次请求前的累计报告阈值，不是硬费用上限；一次在途请求可以超过它，缺失 usage 时不能可靠计量。商品复核不是持锁事务，复核后库存仍可能变化。当前测试没有覆盖所有商品、混合政策问题、多轮购物偏好、并发下架或独立留出集。下一阶段应先扩充这些场景与答案标注，再比较商品关键词、向量和混合检索，避免直接扩大模型调用却没有清晰评价标准。
