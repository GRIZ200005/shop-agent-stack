| 入口 | 地址 | 已实现 |

客户在页面点击“登录账户 → 创建账户”。使用虚拟测试手机号，点击“获取验证码”会自动填入本地体验验证码，不会发送短信。

初始客服用户名 `aster_service`，管理员用户名 `aster_admin`。随机密码保存在本机 `.local/p1-accounts.json`。文件和 `.env` 均被 Git 忽略；请在本地编辑器查看，不要上传 GitHub 或放入截图。重跑初始化不会修改已有账号密码。

三侧入口支持各自登录。客户与员工使用不同令牌，保存在浏览器当前标签页的 sessionStorage；同一标签页的客服和管理员共享员工登录态，切换员工账号时先退出。UI 隐藏入口不是授权，后端每次读取角色和订单归属。

## 2. 推荐体验顺序

1. 客户创建账户，挑选商品并加入购物袋。
2. 打开购物袋，填写虚拟地址，确认创建订单。
3. 在我的订单点击“模拟支付”，订单变为已支付。
4. 点击“申请售后”，填写原因并提交。
5. 在另一个标签页用客服登录，打开对应工单，领取并填写审核说明。
6. 点击“通过并模拟退款”；返回客户页刷新，打开售后查看四个事件与模拟凭证。
7. 管理员登录，新建政策草稿并发布；客户服务政策页可查看发布后的内容。

所有商品、订单与售后列表来自实际 Java API。四款商品为自行创建的合成数据，插画是独立编写的 SVG，无外部图片下载。智能助手入口明确标为准备中，没有模拟 AI 回答。

## 3. 启动、调试与停止

依赖：Docker Desktop Linux engine、PowerShell 7、Node.js 24。本次安装锁定 React 19.3、Vite 8.3、TypeScript 7.0.2，精确解析树见 package-lock.json；Java 17/Maven 仍在容器内。

```powershell
# 在项目根目录，首次或代码修改后
./scripts/start-p1.ps1 -Build

# 已构建，只恢复服务
./scripts/start-p1.ps1

# 停止七个服务，保留数据库及其他数据卷
./scripts/stop-p0.ps1
```

脚本先生成本地账号凭据、启动中间件、幂等应用 `deploy/mysql/migrations/003-p1.sql`，再构建与启动应用。迁移只追加 Aster 表、政策和自建商品，不删除已有业务数据。当前是小规模显式 SQL 迁移，尚无 Flyway 校验和/版本历史；未来变更应追加迁移文件，不能修改旧文件并假设所有数据库会自动变更。

Nginx 将 `/api/portal`、`/api/admin` 转发到 Java 容器，同时托管前端静态产物。它是新增的第七个服务。重建 Java 会短暂停止 API；启动脚本随后重启 Nginx，刷新后端容器地址。所有对主机的端口仅绑定 127.0.0.1。

单独修改前端时可使用热更新：

```powershell
Set-Location apps/web
npm ci
npm run dev
```

开发页为 http://127.0.0.1:5173；Vite 代理到本机两个 Java 端口。开发模式不会自动改变 18030 入口的静态产物，后者需要 `npm run build`。Java断点调试模式尚未配置。

## 4. 业务实现与边界

新增独立模块 `aster-after-sale`，共享给 admin/portal；用 JdbcTemplate 编写显式 SQL 和 Spring 事务，上游商城部分继续使用 MyBatis。Python 不参与业务写库。

售后状态：`SUBMITTED → CLAIMED → REFUNDED / REJECTED`。工单唯一约束绑定订单；同一订单重复提交返回已有申请。领取采用带状态条件的 UPDATE；审核采用行锁与领取人校验，已终结工单不能重复审核。退款金额从订单读取，客户不传入权威金额。

P1 模拟支付在事务中将锁定库存转为实际扣减，重复模拟支付不重复扣减。模拟退款目前将订单关闭、记录退款凭证及审计事件，同一事务提交；它不调用真实渠道。暂未实现退货物流及退款后库存回补，也不将本地字符串凭证视为外部渠道成功证据。

每笔订单只支持一次整单申请，拒绝后不能再次申请；部分退款、补充材料与重新打开工单待扩展。队列/列表当前最多读取 100 条，指标来自当前结果集，不能作为全量运营报表或性能结论。客服可查看本店售后队列，只有领取人可审核；管理员也需先领取。客户不能读取其他客户订单或售后。

政策当前提供新建草稿与发布；尚无正文编辑、旧版本替换、撤回、生效期和索引，这些归后续政策/RAG阶段。账号提供创建时分配角色，尚未实现角色修改、禁用及密码找回。P1 的人工处理是工单领取，AI 写入阻止与会话接管要等 P2 联调。

公开 `/admin/register` 已关闭。Aster 路由要求认证，控制器再校验角色；旧管理接口有额外角色边界。P1 未使用的旧支付、取消入口及 Alipay 路径被拦截，避免绕过当前模拟器。没有全面审计上游全部接口，不应直接部署公网。

上游 WebLogAspect 会包含请求体和登录返回值，本地配置现已关闭该日志与输出无效令牌的 logger；测试 trace 关闭，凭据不加入报告。仍需在将来公开前检查全部仓库历史及产物。

## 6. 从哪里开始学

先亲手跑一遍体验顺序，然后沿一条链路阅读：

`apps/web/src/Customer.tsx → src/api.ts → AsterCustomerController → AfterSaleService.submit → aster_after_sale / aster_after_sale_event`。

接着阅读 `claim` 的条件更新和 `decide` 的行锁，再对照 Playwright 并发领取断言。你应能解释：身份从哪里来、为什么金额由后端读取、重复点击为什么不多建申请、两个客服为什么只有一个领取成功，以及事务回滚保护了哪些数据。这比先通读全部上游代码更有针对性。
