# P4b 退款监控与只读对账

> 验证记录：结果与限制对应文中列明的运行日期及配置。当前使用方式见[工程文档](../README.md)，不同实验结果不合并为统一准确率。

## 本轮能力

客服与管理员工作台新增可展开的“退款监控与对账”。按需加载，不给客户开放。汇总任务总数、待完成、已到投递时间、待人工核实、不一致数量和最早待完成任务等待秒数；每页最多五十条，按 case_id 游标继续加载。

列表展示售后/订单编号、金额、核查结果、当前轮次投递尝试次数和最近受控异常。点击“核对”重新查询单笔记录，显示当前检查结果，不修改任务、订单或账本。

这里的待完成是数据库任务积压，不是 RabbitMQ messages_ready 或 unacked。尝试次数也不是实际退款次数。界面仅在展开、刷新和加载更多时查询，没有后台通知、Prometheus 指标或队列深度采集；不要将其称为完整告警平台。

## 判定范围

范围由 P4 任务、模拟退款账本，以及 REFUNDING/REFUND_REVIEW 售后的 case ID 并集组成，因此可发现部分缺失关联记录。没有 P4 任务/账本的旧版同步退款不进入汇总；单笔检查标为 LEGACY_NOT_TRACKED，未开始退款则标为 NOT_STARTED。

| 结果 | 核查内容 |
| --- | --- |
| CONSISTENT | 任务 DONE、售后 REFUNDED、订单关闭、账本存在且订单/金额/引用匹配，退款完成事件恰好一条 |
| PENDING | 任务 PENDING、售后处理中、订单处于支持退款的状态且金额一致，无账本和退款完成事件 |
| REVIEW | 任务 REVIEW、售后待核实，其他业务基础状态符合待处理条件 |
| MISMATCH | 未满足以上规则，需人工检查，不能直接认定发生资金损失 |

这是本地模拟退款系统的内部一致性检查，不是与支付渠道对账，也不证明没有其他类型的数据错误。发现不一致时不自动重发退款、不修复金额、不改账。

## 后端、权限与错误保留

`RefundDiagnostics` 使用只读、REPEATABLE_READ 事务，单次请求内汇总与明细按数据库一致性快照读取。不同分页请求不是一个长事务，运行中的任务可能在翻页时变化；刷新可获取新的快照。

- GET `/aster/refunds/monitor?before=0`：全范围摘要和最多五十条记录。
- GET `/aster/after-sales/{id}/refund-check`：单笔核查。

两个接口均通过现有 AsterStaffAccess 校验客服/管理员身份。沿用客服可读全局售后队列的权限，未引入多租户隔离。原客服重试权限仍由 P4a 接口独立校验，不因能看监控而增加写权限。

消费者失败在事务回滚后记录 BUSINESS_STATE_CONFLICT 或 CONSUMER_FAILURE；发送失败使用 PUBLISH_UNCONFIRMED。一次 broker ACK 不再清除先前消费异常，只有业务完成或显式重试重置才清除。数据库完全不可用时错误可能无法持久化，但投递仍拒绝并停放，不以记录失败为由确认消息。

## 验证与后续

新增测试覆盖正常待处理/完成/历史记录分类、缺账本、错金额、重复完成事件、只读检查不改状态，以及完成任务不能被迟到的失败记录覆盖。浏览器回归增加真实监控与单笔核对，并检查匿名和客户令牌访问被拒绝。

当前摘要查询含关联与事件计数，在现有开发规模运行；未对百万级记录做容量验收。后续应做 EXPLAIN 和分档压测，再决定汇总表、索引或缓存；不能为减轻查询而缓存资金状态且放弃权威核对。RabbitMQ 深度/死信、worker 活性、阈值通知和定期对账任务仍待完善。

2026-09-15 验收：20 项 Java 测试通过（其中 RefundServiceTest 八项），74 项 Python/MCP 通过、3 项跳过，12 项浏览器通过，17 项 API 冒烟检查完成。匿名和客户令牌均按 mall 既有响应体 code=401/403 约定拒绝，未返回监控记录；初次测试错误地断言 HTTP 状态码，修正后完整回归通过。服务已恢复普通模式，没有新增模型用量。
