# 数据、评测与贡献证明

> 阶段记录：保留当时的方案、结果与限制，不代表当前全部状态。安装和当前能力以[工程文档首页](README.md)为准；后续更新不改写此处原始实验结论。

状态：拟定方案；所有目标待实测。与主计划共同构成 v1.0 验收标准。

## 1. 数据来源与版本

| 数据 | 来源 | 用途 |
|---|---|---|
| 业务种子 | 固定版本的公开 [tau retail 数据](https://github.com/sierra-research/tau2-bench)，加上自建流程数据 | 千级功能场景 |
| 扩展业务集 | 固定 seed 的生成器 | 十万订单性能集；资源允许再做百万级扩展 |
| 政策/FAQ/SOP | 为虚构商家自建，人工审核 | 起步 40–80 篇语义一致的内容 |
| 商品说明 | 自建商品规格，必要时加入许可明确的公开说明 | 选购、对比、公开资料查询 |
| 任务与金标 | 人工设计的独立业务场景族，模型辅助改写 | 评测，不进入 prompt 或知识索引 |
| 网络快照 | 可核对公开来源的固定 fixture | 离线回归；真实联网另验收 |

数据源仓库存在任务与版本更新，应固定 commit/release；模型、数据版本和工具契约一起记录。使用改造后的任务只发布 Aster 自建成绩，不与原始 tau 排行榜直接比较。

原订单状态与新商城模型必须通过语义映射转换，不能把旧 pending 一律视为待付款。校验支付、履约事实，保留 ID 映射和拒绝导入报告。业务数据是模拟或合成，不声称真实客户量。

商品图片使用自己制作、明确许可素材或合法占位图，记录来源；没有许可的商品网页图片不批量迁入发布仓库。

## 2. 生成与一致性

生成会员、商品、SKU、订单、明细、支付、售后、退款任务；控制热点、时间、状态、金额、部分退款和异常比例。测试管理员与客户使用独立身份，不依赖共享默认账户。

强制校验：关联有效、累计退款不超过实付、SKU 数量合法、状态转换可达、状态与时间一致。大批量入库用于性能；经真实业务 API 生成的小集合用于验证交易生命周期，两者区别标注。

manifest：生成器 commit、seed、数量、分布、校验结果、文件 hash、来源与许可。知识文档记录 doc_id、clause_id、version、effective_from/to、visibility、source、content_hash。索引版本可回滚，撤回内容应在检索可见性上及时失效。

## 3. 评测集

起步 360 个独立场景族：

| 类别 | 数量 |
|---|---:|
| 选购/商品对比/订单查询 | 50 |
| 本店政策、无答案、版本冲突与重检索 | 70 |
| 多轮确认、售后提交与人工接管 | 80 |
| 越权、提示注入、确认篡改 | 70 |
| 超时、消息重投、重连、恢复 | 60 |
| 公开网络查询与来源选择 | 30 |

按场景族划分开发/验证/锁定测试集为 180/60/120；相同模板和问题改写不得跨集合。每类按比例划分，发布明确分母；必要时扩充稀有失败类别。

每个样例保存：初始 fixture、用户身份、目标与轮次、允许和禁止的副作用、相关条款 ID、预期业务状态、预期 UI 终态、故障注入配置。固定时钟避免退货期限测试漂移。

锁定测试标签不用于 prompt 调参。可以检索政策原文，但不能将测试问答标签加入知识库。一次测试反馈被用于修改后，最终报告说明该测试已被观察，并为泛化判断补充独立 holdout。

## 4. 评分器与自动化测试

评分器先通过反例：只计划不执行、错误工具参数、错误订单、错误金额、重复退款、错误引用、缺失日志必须失败。不能靠模型自己说成功。

业务用数据库及 Java 审计判定，工具执行用实际结果判定，所需任务可接受不同正确轨迹。异常与超时计失败，日志缺失单列失败原因，不默认通过。

- JUnit + [Testcontainers](https://java.testcontainers.org/)：真实 MySQL/Redis/MQ 的事务、锁、唯一约束和投递测试。
- Python 测试：Agent 子图、检索路由、预算和 fixture 回放。
- 浏览器 E2E：三侧登录、选购下单、确认、审核、退款、断线、转人工。
- [k6](https://grafana.com/docs/k6/latest/using-k6/thresholds/)：普通 API、固定延迟桩的编排、真实模型有限并发分开测试。
- MCP 集成：真实 SDK 初始化、发现、调用、鉴权、超时与连接重建，不只直接调用内部 Python 函数。

LLM judge 仅辅助表达质量与证据支持判断，记录模型与 rubric；人工抽查至少 20% 和全部分歧。金额、权限、退款与状态由确定断言处理。

## 5. 指标口径

| 指标 | 定义 |
|---|---|
| 端到端任务成功率 | 目标达成且全部禁止副作用未发生的任务数 / 总任务数 |
| 工具执行正确率 | 身份、参数、实际结果均正确的调用数 / 总实际调用数；另报必要动作覆盖率 |
| 未授权副作用率 | 发生非法状态变化的攻击任务数 / 攻击任务总数 |
| 重复有效退款率 | 产生重复有效退款的测试请求数 / 重复请求测试数 |
| Recall@5 | 前五检索结果覆盖的相关条款数 / 金标相关条款数，在检索样例上宏平均 |
| 引用支持率 | 引用实际支持的可核查断言数 / 带引用断言数；另报引用覆盖率 |
| 重检索收益 | 固定首次检索失败子集上，补查后新增成功数及额外 token/耗时 |
| 无效搜索率 | 不需要外部信息却触发网络搜索的样例数 / 对应样例总数 |
| 恢复时间 | 故障解除到业务正确收敛的时间；另报滞留、重复、错误数量 |
| 延迟 | 普通 API p50/p95/p99、首个有效内容、完整答复、业务完成分别统计 |
| 成本 | 全部尝试含重试的模型/搜索成本 / 成功任务数 |
| 前端恢复正确性 | 重连后的重复/丢失事件数、错误终态数与恢复耗时 |

模型生成文字首字不等于业务完成；状态占位事件不算首个有效内容。工具调用次数减少只有在成功率和安全门槛保持时才是正向优化。

拟定首版门槛：锁定测试集成功率 >=85%；专项测试中非法写入与重复有效退款观测数为 0；需检索样例 Recall@5 >=90%。这些是工程门槛，样本内零事故不代表普遍零风险。

性能先固定环境，逐级 10/30/50 并发；记录请求速率、吞吐、错误率、测试时间、预热、CPU/RAM、冷热缓存和数据集。非 AI 读取 API 可先以 p95<300ms、错误率<1% 为候选预算，P0 基线后确定。真实模型按查询/多轮/写操作分类，不承诺统一延迟。

前端用固定浏览器和数据测试 1,000 条会话记录、动态卡片、断线 5 秒后恢复；记录性能 trace 和 DOM 规模。先验证无重复、无串会话和终态正确，再优化渲染。

## 6. 对照实验与报告

在相同 Java 底座和安全校验下比较：

1. 简单工具调用 + 无检索（仅用于相应可回答任务）。
2. 一次 Hybrid RAG。
3. 有界 Agentic RAG。
4. Agentic RAG 加网络分支（仅在需要外部信息的任务比较）。

另做有/无重排、工具连接复用、上下文预算、独立读取并发的局部实验。不能通过关闭授权获得所谓高成功率；危险消融只在独立 fixture 中验证，不接真实资金。

每配置至少 3 次，按场景配对比较并报告置信区间；同模型、同版本、同数据、同预算。网络回归用快照，实时联网 smoke 单列日期，不混为静态模型提升。

运行 manifest 包括代码 commit、数据 hash、模型 ID、provider、温度、预算、检索配置、环境规格、价格日期、测试 seed。保存原始日志和失败分类，不只留百分比。
