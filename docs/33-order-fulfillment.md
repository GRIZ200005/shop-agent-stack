# 订单履约与 V1 收尾范围

2026-09-16。目标是可复现、可演示、可解释的个人 AI + 后端项目；当前不是商业生产系统。本阶段没有增加付费模型调用或新的模型评测矩阵。

## 本轮可用流程

1. 客户在 `/app` 选购商品，在 `/app/orders` 完成模拟支付。
2. 管理员登录 `/admin/orders`，默认查看待发货订单，可按订单号、状态筛选，每页20笔。
3. 点击「查看履约」，核对商品快照和收货地址，填写配送备注，点击「确认模拟发货」。
4. 系统填写「星序模拟配送」及 `SIM-ASTER-订单ID` 单号，订单进入配送中。管理员可再记录一次「模拟派送中」动态。
5. 客户点击订单卡片的「查看物流」，可查看模拟单号和按顺序保存的配送动态，点击「刷新动态」获取更新。
6. 客户点击「确认收货」，二次确认后订单进入已完成。确认操作不重复扣减库存，不修改支付金额；库存扣减仍发生在既有模拟支付环节。

有未被拒绝的售后记录时，暂停继续发货/派送/首次确认收货；已关闭订单也不能发货。已拒绝的售后允许继续履约。客户确认收货不意味着丧失现有售后申请能力。

## 实现与边界

- 原创 `FulfillmentService`、管理员 `AsterFulfillmentController`、客户 `AsterShipmentController` 和 `Fulfillment.tsx`。继续使用现有 Spring Boot/JDBC、MySQL和React，不增加依赖。
- `aster_shipment_event` 使用自增ID保留事件顺序，并对 `(order_id,stage)` 建唯一约束。目前一单一个模拟包裹，节点为 `SHIPPED → DELIVERING → RECEIVED`；客户可在已发货后直接确认，不强制管理员先填写派送动态。
- 操作先锁定订单行，检查状态及售后，再在同一事务内更新订单和事件。并发发货只有一个请求创建节点；相同管理员和备注重试视作成功，改变已有节点内容则拒绝。客户重复确认不再生成事件，先检查所有权再判断是否重复。
- 售后查询不再锁售后行，避免与既有退款的「售后行→订单行」加锁顺序反向等待；新增售后申请原本也会锁订单行。这里不是对全部上游履约、支付、取消接口的全面并发审计。
- 管理员每个接口执行当前角色检查。客服不能发货或访问管理员履约列表。客户详情、确认接口只使用登录身份，不能读取或确认别人的订单。
- mall 的旧 `confirmReceiveOrder` 服务方法也委托给同一履约状态机，避免绕开事件记录和售后检查。保留原作者及修改说明。未经过本模拟发货链路、没有 `SHIPPED` 事件的旧订单不会凭空生成物流或直接确认。
- 展示收货地址只在授权订单详情中进行；列表不批量展示地址。展示订单已有商品快照；旧测试订单缺少名称时显示商品编号，图片缺失沿用现有占位，不伪造历史商品资料。
- 本阶段不连接快递公司、不预约真实揽收，不支持分包、改址、自动签收、物流回调、推送通知。配送节点是管理员录入的模拟记录，不能当作真实快递轨迹。原来的后台管理接口并未全部迁移到新流水中。

## 部署与必要验证

`deploy/mysql/migrations/010-order-fulfillment.sql` 已接入 `scripts/init-p1.ps1`，当前本机已迁移和部署。入口沿用 `scripts/build-p0.ps1`、`apps/web` 下的 `npm run build` 以及既有Compose启动流程。

- Java 聚焦回归 **35项通过**，包括新增4项：状态机、幂等、所有权、未支付/售后冲突、非法转换以及两管理员竞争发货。
- Playwright `tests/fulfillment.spec.ts` **1项完整浏览器链路通过**，覆盖注册→下单→模拟支付→管理员发货与派送→客户确认收货，同时验证客服越权、他人订单访问、重复发货/确认和已记录节点不可覆盖。
- 已检查管理员、客户及窄屏截图。视觉检查发现极简测试购物袋缺少商品快照后，补全了验收夹具并添加缺失名称兜底，重新构建和通过该链路测试。
- 验收数据来自合成用户/地址/商品；测试使用正常模拟支付，会扣减一件测试商品库存，并保留已完成订单和事件作为业务记录，不伪造退款或直接回填已完成订单库存。

没有本轮真实模型准确率、生产吞吐量或真实物流服务的测试结论。

## V1 接下来只保留两块收尾

为避免不断新增功能，先以现有业务范围完成 V1：

1. **整体验收与缺陷修复**：按固定演示脚本串联客户购买、Agent查询/政策问答、人工咨询、售后模拟退款、商品管理和履约；修复阻断使用的问题。复用已有验证，只补暴露出的关键缺口，不再扩张评测矩阵。付费模型验证继续遵循已有显式授权边界。
2. **复现与讲解材料**：核对启动/停止/配置说明，列出环境依赖及已知限制，整理架构图、关键请求链路、个人改动和有依据的指标。公开仓库前单独检查完整历史、许可证、敏感信息和生成产物。

两块收尾完成后进入正式学习：以实际链路串起 REST API、Spring事务、MySQL索引与锁、Redis、RabbitMQ、Agent上下文与RAG、测试和故障处理。真实支付、多仓库、分包、复杂促销以及更大规模部署留作后续版本，不作为 V1 学习启动的前置条件。上述范围不是对工作时长或生产就绪程度的保证。
