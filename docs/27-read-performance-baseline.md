## 范围与复现

服务启动且本机已生成体验账号后运行：

```powershell
./scripts/benchmark-read-api.ps1
./scripts/capture-read-plans.ps1 -OutputDirectory '<上一命令输出的绝对运行目录>'
```

负载容器通过 Nginx 调用 Java 服务。商品列表匿名读取，退款监控使用现有客服账号；登录后只读业务数据，不调用模型，不创建订单或退款。账号从被忽略的本机文件读取，报告不输出凭据或响应正文。不要与故障注入、数据生成或其他压测同时运行。

每个接口依次使用 1、5、15 个并发 worker，每个 worker 请求 30 次，重复 3 轮，并交替接口先后顺序。计入统计 3,780 次请求，另有 30 次预热和 1 次登录。闭环请求无思考时间，超时 10 秒，阶段错误率超过 5% 后停止后续阶段。

成功要求 HTTP 状态、业务 code 和响应结构同时通过；HTTP 200 下的鉴权错误不算成功。错误率分母为全部完成请求，延迟包含失败请求；P50/P95/P99 使用 nearest-rank，完成 RPS 为请求数除以阶段墙钟时间，同时记录成功 RPS。2 个评分器测试已通过，覆盖业务错误识别和失败延迟统计。

## 数据规模与 SQL 证据

MySQL 8.4.9，buffer pool 128 MiB，max_connections 151。采集时商品 4 行、售后 73 行、异步退款任务 4 行、模拟退款流水 4 行、售后事件 170 行。

执行计划采集使用只读会话。退款 SQL 从当前 Java 查询中提取，商品投影从 MyBatis mapper 提取；商品条件、分页对应本轮固定搜索请求。保存实际 SQL 及源文件 SHA256，代码变化导致提取失败时应人工核对。

商品 count 和列表扫描 4 行，单次执行分别约 0.357 ms 和 0.0183 ms；退款汇总约 0.858 ms，使用现有索引和主键关联。这里没有证据表明全表扫描已经造成瓶颈，也没有据此新增索引或 Redis 缓存。本轮没有开启全局慢查询日志，EXPLAIN ANALYZE 的单次计时也不等于接口延迟。
